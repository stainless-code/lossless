LCM ships as three packages. `lossless-core` is the engine: the store, the summary DAG, the thresholds, the recall tools, and the metrics. `pi-lossless` runs it inside Pi, and `opencode-lossless` runs it inside OpenCode v2. The engine imports no agent SDK, so every line of harness-specific code sits on an adapter's side of a contract the engine states as two ports.

## A harness is the agent LCM runs inside

A harness owns the session file, the model calls, the tool loop, and the screen. Pi and OpenCode each own those for their own process, and LCM owns none of them, so the engine asks its host for each one. A second harness is therefore a second adapter, not a second engine.

## Two ports carry what the engine cannot do itself

| Port        | The question it answers                    |
| ----------- | ------------------------------------------ |
| `ModelHost` | Which model, and what did it answer        |
| `Reader`    | What the reader asked for, and what it said |

`ModelHost` names the session's model, resolves a model named in config, and runs one completion from a prompt the engine already rendered, so a host cannot change what the summarizer is asked. Notices travel the same way: a host with no user interface reports `none`, so the engine has one branch to write.

`Reader` is one retrieval conversation. `begin()` returns a reading whose `next()` appends the tool results the caller ran and returns the model's reply. That keeps a read out of the main loop. OpenCode's plugin API has no tool-calling completion, so its adapter does not implement `Reader`; `lcm_expand_query` runs as a child session instead.

The engine asks for nothing else. Its boundary test fails the first module under `src/` that imports an agent SDK or a specifier outside `node:*` and `typebox`, so the contract cannot erode quietly.

## Each adapter owns its harness's surface

`pi-lossless` holds:

- the Pi hooks: `session_start`, `message_end`, and `turn_end` feed messages in, `context` swaps the aged head between turns, and `session_before_compact` takes over at Pi's compaction limit
- the model host over Pi's model registry, and the notices that reach Pi's interface
- Pi's session files and home layout, which decide which store a session opens
- the `/lcm` command and the settings cockpit, from `/lcm status` to `/lcm settings`
- `lcm_grep`, `lcm_describe`, and `lcm_expand_query`

`opencode-lossless` holds:

- the OpenCode hooks: `session.prompt` and `session.text.ended` feed the mirror, `execute.after` records tool traffic, `session.context` swaps the aged head, and `session.compaction` returns the checkpoint
- the model host over `generate.text`
- the sidecar directory and per-session SQLite store, which decide where a session's history lives
- `/lossless-status`, `/lossless-report`, and `/lossless-pass`
- `lcm_grep`, `lcm_describe`, `lcm_expand`, and `lcm_expand_query` through a child session

Every hook name in either list is its harness's, and the engine never sees one. `session_tree` lands in the Pi adapter too, marking the entries an abandoned branch took out of context and clearing the mark when a later turn returns to them.

Each adapter packs the engine into its own `dist/index.mjs`, and neither manifest declares a runtime dependency. Pi's bundle imports only packages Pi already has; OpenCode's bundle names no host SDK.

The OpenCode adapter also brings a sidecar directory and one SQLite file per session, because OpenCode has no Pi session file to derive a store path from; a cross-session scan over that directory, because the engine's Pi session listing reads Pi's JSONL header; and a child-session reader. A third harness would supply its own equivalents.
